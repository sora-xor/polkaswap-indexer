## Deployment paths

- **Recover existing data:** Verify an off-host backup and restore, add capacity, investigate the damaged index, reconcile the anomalous checkpoint, and migrate into a `C`-collation database. This path depends on restoring trustworthy existing state.
- **Parallel fresh rebuild:** Provision a container-capable target with adequate storage and a new `C`-collation PostgreSQL database. Preserve the old data and API, with the failing worker suspended, while the candidate reindexes from its reviewed first required SORA block through a complete independent archive RPC. Switch traffic only after a fresh mainnet checkpoint, full public smoke, retained mobile compatibility, and rollback have been demonstrated. This avoids using the corrupted index or missing checkpoint as migration input, but requires a complete archive, time and capacity for the full backfill, and a preserved old service for rollback.

## Recovery order for existing data

1. Preserve the verified off-host logical dump and identify any provider snapshot or stronger point-in-time backup. Record backup time, the completed data restore test, missing full-service restore coverage, available disk, rollback owner, and the exact production database target. Preserve the existing data and prior release.
2. Investigate the storage fault and affected index. Check the underlying volume and PostgreSQL logs, then use a targeted integrity check and a disk-space plan. [PostgreSQL 16 `REINDEX`](https://www.postgresql.org/docs/16/sql-reindex.html) can rebuild a damaged user index, but a concurrent rebuild scans the table twice and adds substantial I/O; a regular rebuild blocks writes and most reads that need the index. Plan the operation against the verified backup and capacity before execution.
3. Reconcile the anomalous checkpoint at block 27,159,179 with its indexed documents and the preceding complete snapshot. The deployed code wrote each block's documents, `BLOCK` snapshot, and `chainState` in one PostgreSQL transaction, so the missing snapshot is not explained by an ordinary failed block write. Establish a coherent recovery point before allowing the candidate worker to migrate `chainIdentity`. A pointer-only rewind could double-apply derived account and aggregate updates.
4. Resolve the `en_US.UTF-8` versus `C` collation mismatch through a reviewed migration onto a suitably sized database or a proven compatibility design. Select a container-capable target for the current reviewed Compose release. Do not run the candidate migration against the current table as-is.
5. Provision reviewed, distinct primary and independent archive WSS endpoints and role-separated PostgreSQL credentials. Set the five explicit mobile capability values with sends and mutations closed until mobile admission passes. Review the TLS edge controls and rollback path.
6. Complete review and green CI for PRs #11 and #12, stage the immutable release artifact, run the direct identity preflight again, switch the worker/API, and run the full public production smoke. Record deployment identity, artifact digest, fresh checkpoint, RPC/TLS controls, and operator attestation before opening release gates.
